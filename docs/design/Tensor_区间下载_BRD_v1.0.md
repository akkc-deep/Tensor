## 1. 业务背景

当前 Tensor 接入 49 个 Tushare Pro 接口：19 个按交易日期、15 个按公告日期、1 个按月份、3 个按原生日期范围下载，其余 11 个使用证券、交易所等条件或无需参数。用户希望一次选择区间，避免逐日、逐月反复操作。

区间扩大后，个别股票或日期可能遇到网络、限流或数据错误。用户希望批量获取时保留已确认提交的成功成果，将明确失败项保存在同一任务中，后续只重试实际失败范围。重试仍失败则保留原项，成功删除。任务说明插件、接口、失败对象、时间及原因；后续单股下载沿用同一模型。

交易日、公告日、报告期、月份的含义继续区分。新增重试能力不改变接口原有筛选条件，也不证明上游具备尚未核实的历史数据能力。

## 2. 业务目标与成功标准

| 目标 | 成功标准 |
|---|---|
| 减少操作 | 合法区间一次提交，按来源能力批量取数；重试只处理已保存失败范围 |
| 保留成功 | 能独立确认结果的股票时间单元分别入库，同一批量响应中某股失败不撤销其他已提交单元 |
| 失败准确 | 失败记录包含对象、时间和原因；无法可靠定位时保留完整恢复范围，不猜测逐股失败 |
| 结果可信 | 成功、合法空、失败、未开始及提交未知分别说明；只按确认提交的数据统计成功 |
| 可查看与重试 | 已保存失败在刷新或重启后可查看；复用原任务，成功项删除，全部解决后任务移除 |

日期输入仍最多 31 个自然日；19 个交易日期接口先确认适用日历，38 个区间接口与 11 个原条件接口的范围不变。不承诺固定下载速度、全部账号权限或完整历史覆盖。

## 3. 核心场景

| 场景 | 期望结果 |
|---|---|
| 同一批量响应含 A、B、C 三只股票，B 有局部错误 | 整体及单元完整性、独立重试条件满足时，A／C 独立入库，只记录 B＋失败时间 |
| 两只股票同一天失败 | 同一任务保存两条明细；一只成功只删除它的明细，另一只继续保留 |
| 整个请求超时或后续页失败 | 不将部分响应当成功；能确认受影响独立单元时完整记录，否则保存原请求范围，不能只猜一只股票失败 |
| 仅能整范围处理的接口，某行错误使事务失败 | 保存整个恢复范围，原因可指出具体股票；不遗漏同范围内其他未提交数据 |
| 合法空或休市 | 完整确认后视为完成，不产生占位或失败项；不把少一只股票或少一天直接当作失败 |
| 来源限流、超时或其他下载错误 | 保存实际失败范围，继续后续下载直至计划范围全部尝试；保留已提交成果 |
| 数据库不可用、记录保存失败或提交未知 | 按系统故障规则停止并说明；未开始范围不保存为失败，不虚报已保存 |
| 手动重试 | 只处理已保存的对象及时间，成功原子删除明细，仍失败更新原因，不生成父子任务 |

## 4. 业务范围

### 4.1 本次包含

| 接口组 | 数量 | 下载及恢复语义 |
|---|---:|---|
| 交易日期接口 | 19 | 先确认日历；可独立恢复时按股票及实际交易日期／范围记录，否则保留完整范围 |
| 公告日期接口 | 15 | 使用公告语义，不用报告期／解禁日期替代；独立恢复须有来源证据 |
| 月度推荐 | 1 | 覆盖完整月份，保留月度粒度 |
| 原生范围 | 3 | 保留原生含义；无独立恢复依据时整范围重试 |
| 保留原条件 | 11 | 不增加时间参数；单股或整个原条件恢复项均使用无时间语义 |
| 合计 | 49 | 38 个区间目标＋11 个原条件，均纳入失败恢复设计，不表示均已实现或真实可用 |

包含表单、日历过滤、批量获取、独立成功保留、失败列表与详情、原任务手动重试及现有只读查看。每次仍选择一个插件和接口，不跨首次操作合并任务。

### 4.2 本次不包含

定时调度、自动重试、取消／暂停、实时进度、完整历史中心、父子任务、未执行项预登记、完整中断恢复、数据编辑／导出或新数据源。后续新增单股下载入口和股票集合选择方式单独设计，本版仅统一恢复语义。

### 4.3 请求批次与恢复单元

请求批次负责合法批量取数，可含多个股票、日期及分页。恢复单元负责独立校验、原子入库和重试，可为股票＋日期、股票＋时间范围，或整个原请求范围。一次 HTTP 请求可以包含多个恢复单元，因此可出现同一响应内部分单元成功、部分失败。

独立恢复必须同时具备可靠的对象和时间归属、完整性依据及合法单独重试方式；不满足时整体作为一个单元。恢复单元内部仍全部成功或全部回滚；不能按错误原因中的一只股票缩小一个已整体回滚的范围。请求失败时不凭不完整响应推测所有股票各自的业务状态。

来源事实见 [批量下载调研](../research/2026-09-08-tushare-range-batch-research.md)；该调研中旧“下载与事务同批”决策已被本版替代，来源能力摘录仍保留。34 项区间参数描述等公开信息不等同于已验证逐股结果或独立恢复能力。

## 5. 业务流程

1. 校验插件、接口、日期上限及原条件；交易日期先确认全部适用日历。业务执行前校验失败不创建失败任务。
2. 规划合法请求范围及恢复策略，在内存执行，不预先保存待处理项。
3. 获取当前请求完整数据，完成整体协议、分页和归属检查；依据可靠策略形成恢复单元。
4. 逐单元完整校验并批量入库；可隔离错误只使该单元失败，已提交单元保留。首次明确失败才创建任务，后续失败关联同一任务。
5. 当前请求的单元处理完毕或其明确失败范围保存后，继续下一请求，直至全部计划范围都已尝试；来源级错误不跳过后续范围。数据库不可用、记录保存失败或提交未知时停止并说明，不虚报失败已保存。
6. 本轮响应按恢复单元展示成功、失败、未开始及已提交记录数；只为已保存的失败提供任务入口。
7. 用户手动重试失败对象及时间；成功删除对应明细，最后一项解决时删除任务，仍失败只更新原因。原 REQUEST 失败范围不在重试中改成部分范围。

### 6.1 休市规则

使用适用交易所／业务日历，覆盖周末、节假日及特殊休市；不能用普通工作日历或个股停牌替代。多市场仅在适用范围均休市时跳过整个日期。首次必要日历失败时业务请求为零，不创建失败任务；已有任务重新确认失败时保留原明细。公告、月份及原生／原条件接口不误用休市过滤，交易日历业务数据保留休市行。

### 6.2 恢复范围

股票和日期可定位不等于已经能独立恢复，仍需确认完整性和合法请求方式。A／C 成功、B 失败时只保存 B；A／B／C 同属已回滚单元时保存全部范围。不能将不同失败日期合成首尾连续区间，也不能将已提交单元重新包进整批失败项。

同一任务使用原插件当前凭证；不保存 Token、原始响应或堆栈。插件或参数不可执行时保留失败项并说明原因，用户修改条件属于新下载操作。

## 7. 约束与实施前核实

单实例同步执行，每轮用户手动发起；不引入队列或后台恢复。每个独立单元仍批量写入，其内部全部 SQL 原子提交。失败明细重试成功删除；重启后只保证已保存失败可查看，不从业务表推算未保存任务。

后续按接口核实日历、日期含义、取全方式、对象归属、单元完整性及单独重试能力。两表生命周期和事务规则已确认，具体技术方案见 [TRD §5](Tensor_区间下载_TRD_v1.0.md#5-日历与上游完整性)、[§7](Tensor_区间下载_TRD_v1.0.md#7-失败任务的数据模型与事务)。

## 9. 依赖与风险

独立恢复依赖逐接口证据，不能因为有股票代码列就默认支持。记录失败或进程退出可能留下未保存范围；仅失败记录方案不提供完整恢复保证。跨次更新沿用已有业务规则，不能从失败表证明过去成功内容。

[ISSUE-008](../issues/problems/ISSUE-008-tushare-live-coverage-gap.md) 的 9 项继续“不依赖，未解决，用户后续单独处理”；不恢复真实调用安排，不改变历史验收。
