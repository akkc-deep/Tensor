# Tensor 可扩展数据校验方案

- 日期：2026-09-17。
- 状态：用户已确认方案方向，本次提交将方案归档；文中的新增配置和能力尚未实现。
- 审查基线：`main`，提交 `21e9603fa5d5c7408fed4007744854607afa614f`。
- 适用范围：当前 40 个 Tushare 接口，以及后续新增接口和数据源。
- 核心选择：接口专属策略 + 通用规则库 + YAML 配置 + Java 规则扩展。

## 1. 用通俗的话说明

给不同的数据配不同的“检查清单”，由统一程序执行：检查已存的数据对不对、计划下载的范围有没有完成、应该存在的记录有没有漏掉。每个问题分别给结论。

例如：最高价低于最低价是数据错误；停牌期间没有日线可能正常；没有分红事件时可以没有分红记录；缺少停牌依据时只能说无法判断。新增规则时，已有算法改配置，新的复杂算法增加独立 Java 实现。

## 2. 当前代码中已确认的限制

本节是指定提交的静态审查结论，不代表已经复现生产数据库中的失败，也不表示数据已修复。

| 当前行为 | 代码依据 | 影响 |
| --- | --- | --- |
| 33 个股票级接口使用直接返回 `UNKNOWN` 的通用覆盖规则 | `TushareIntegrityPolicies`、`TushareIntegrityCoverageRule` | 数据正常也无法得到覆盖通过结论 |
| `daily`、`weekly`、`monthly` 生成的预期集合始终标为 `UNCONFIRMED`，规则返回 `UNKNOWN` | `TushareMarketIntegrityRule` | 有候选日期和疑似缺口，但不能确认整体覆盖通过 |
| `trade_cal`、`margin`、`slb_len`、`index_classify` 属于 `NON_STOCK`，执行器直接跳过 | `IntegrityCheckRunner` | 没有按交易所或全局范围执行真实检查 |
| 接口日期轴集中硬编码，并要求恰好 40 个接口 | `TushareIntegrityPolicies` | 新增接口必须修改集中策略代码 |
| 已有 `IntegrityRule`、描述信息、版本和依赖声明 | `tensor-plugin-api` | 可以在现有扩展点上演进 |

当前页面将 `UNKNOWN` 显示为“无法判定”，将 `FAIL` 显示为“有问题”。上述覆盖限制不能直接解释“全部 FAIL”。实施前必须取得真实失败报告，核对应用版本、接口、规则 ID、`reasonCode`、业务键和实际值，重点区分必填字段、业务键、来源身份错误及规则执行异常。

行情测试中已有 `comparisonIsAlwaysUnconfirmedAndResultNeverUpgradesFromUnknown`，明确约束旧行为。调整时应新增“证据充分可判定”的用例，并保留“证据不足仍未知”的用例，不能直接把 `UNKNOWN` 改成 `PASS`。

## 3. 三个独立的检查维度

| 维度 | 要回答的问题 | 例子 |
| --- | --- | --- |
| 记录质量 | 已入库记录是否满足数据合同和业务规则？ | 业务键重复、来源标识错误、最高价低于最低价 |
| 采集覆盖 | 固定计划中的请求、分片和入库是否完成？ | 漏请求日期、分页不完整、响应与入库不一致 |
| 业务完整性 | 在指定来源、范围、时点下，应有记录是否齐全？ | 已确认应有行情的日期缺少记录 |

三个维度独立展示。例如：“记录质量通过；采集完成；业务完整性待核实”。来源对账是支撑这些结论的检查方式，报告单独保留其结果与证据。

已有记录检查通过不代表没有漏数；下载成功不代表来源返回完整；本地与来源相同也不代表来源数据绝对正确。规则的结论只对记录的范围、字段、来源版本和检查时点负责。

## 4. 当前 40 个接口的策略矩阵

每个接口复用基础规则，再叠加接口专属规则。下表覆盖当前 [manifest](../../data-template/manifest.json) 的全部 40 项；同一类别内仍需为每个接口声明自己的字段、频率、合法空值和适用条件。

| 类别 | 接口 | 专属策略 |
| --- | --- | --- |
| 基础快照 | `stock_basic`、`stock_company` | 主键、代码与市场映射、条件必填、快照新鲜度；历史完整性需有历史快照和证券生命周期依据 |
| 交易日历 | `trade_cal` | 按交易所检查自然日覆盖、日期唯一性和开闭市标记；休市日同样需要日历记录 |
| 日／周／月行情 | `daily`、`weekly`、`monthly` | OHLC 关系、数量金额、价格口径；日线结合日历、上市退市、停牌和发布时间，周月线按已结束周期及来源日期口径核对 |
| 每日指标及衍生数据 | `daily_basic`、`adj_factor`、`moneyflow`、`stk_limit` | 独立声明证券范围、历史起点、合法空值、数值关系和跨表口径，不能全部套用 daily 的应有日期 |
| 财务报表 | `income`、`balancesheet`、`cashflow`、`fina_indicator`、`fina_audit`、`fina_mainbz` | 区分报告期、公告日、报表类型和修订版本；按公司类型、披露频率及字段适用性选择规则 |
| 事件数据 | `forecast`、`express`、`dividend`、`disclosure_date`、`repurchase`、`stk_holdertrade`、`block_trade`、`top_list`、`suspend_d`、`new_share` | 检查事件业务键、日期关系、状态与金额；没有事件的日期允许无记录，完整性需采集证据或来源对账 |
| 股东、质押与管理层 | `top10_holders`、`top10_floatholders`、`stk_holdernumber`、`pledge_stat`、`pledge_detail`、`stk_managers`、`stk_rewards` | 分别按报告期、统计期、公告或任职区间检查，不统一要求每天有数据 |
| 两融及转融通 | `margin`、`margin_detail`、`slb_len`、`slb_sec`、`slb_sec_detail` | 区分交易所汇总和证券明细，核对适用证券范围、业务及来源服务有效期；历史数据仍可做记录质量检查 |
| 行业分类及成员 | `index_classify`、`index_member_all` | 分类层级、引用关系、成员生效与退出区间；历史成员按有效区间重叠判断，不能仅筛入选日期 |

共同约束：

- 日期轴必须显式声明，区分交易日、公告日、报告期、发行日和生效日。下载参数的日期轴不能直接替代业务校验日期轴。
- 快照表只能直接证明当前快照。当前上市名单不能证明完整的历史证券全集。
- 现有 `stock_basic` 未保存 `list_status`、`delist_date`，不能直接构造完整上市退市区间；先检查实际元数据并补充独立生命周期证据。
- 合法空值按接口、字段、公司类型及生效时期定义。`daily_basic` 的亏损 PE 可为空，不能把全部数值字段强制非空。
- Tushare `daily` 停牌期间不提供数据。停牌依据必须区分全天、盘中及复牌语义，不能看见一条停牌记录就删除整个日期。
- 同期财报可有不同类型和修订版本，唯一性依据完整业务键。不能把每个财务接口都设为每季度恰好一条。
- 公式核对需固定单位、币种、复权方式、报表版本和时间口径；使用十进制数及明确容差。净流量、利润等允许为负的字段不能复用非负约束。
- 数值突变和统计离群默认报告 `WARN`，不统一硬编码涨跌幅或行数阈值为确定错误。

## 5. 完整性的判断依据

### 5.1 业务推导的预期集合

由数据源专属的预期集合提供器生成完整业务键。日线需综合适用交易日历、历史证券范围、上市退市、全天停牌、来源服务历史边界、已发布时间及允许延迟。

输出包含预期键、声明范围、依据是否充分及证据引用。优先沿用现有 `IntegrityExpectedKeys` 的 `PROVEN / UNCONFIRMED` 语义。参考材料不完整时返回未知或候选缺口，不能升级为确认完整。

原始参考表存在、下载任务成功、用户勾选“可信”，都不能单独证明全集可靠。数据源提供器应验证依据覆盖范围与适用性，核心检查业务键、范围及快照一致性。依据只覆盖部分范围时，只对已证明范围给结论，其余范围保持未知。

### 5.2 采集证据

复用已有下载任务、计划和批次记录；不足的字段作为后续实施增补。保留请求参数及隐式默认值、计划范围、最终叶子分片、分页或拆分终止依据、响应行数、规范化去重结果、成功入库数量、拒绝记录及失败原因。

成功计数不以 MySQL affected rows 直接代替：upsert、重复记录和更新会改变这个数的含义。需要比较规范化业务键及选定字段，才能证明响应已正确落库。

区分“未请求”“成功空响应”“来源权限或限流失败”“返回可能截断”“写入失败”。空响应与执行失败不能互相替代。

### 5.3 来源对账

作为独立任务拉取并归档固定范围的来源参考快照，记录获取时点、参数、字段、权限、分页或分片完整性、来源修订及摘要，再由本地校验读取证据。

保留现有本地规则不访问上游的约定。来源不同步、版本不可比或返回可能截断时，相关完整性仍为 `UNKNOWN`。来源修订差异先区分更新时间，不能直接认定历史本地记录错误。

事件表本地为空时，记录质量规则无行可检查，采集覆盖按任务证据判断，业务完整性在没有可靠全集时保持未知。只有已证明预期为空且本地为空，才能标记“已验证为空”；覆盖率显示不适用，不伪造 100%。

## 6. 可扩展实现方式

### 6.1 方案选择

| 方式 | 特点 | 决策 |
| --- | --- | --- |
| 全部 Java 硬编码 | 复杂算法容易实现，参数与启停也需改代码 | 不作为整体方案 |
| 全部配置或表达式 | 简单规则易调整，复杂业务容易变成难维护的配置语言 | 不作为整体方案 |
| Java 算法 + YAML 配置 | 通用规则复用，复杂规则保留清晰代码边界 | 采用 |

首版使用现有 Java 插件体系，不引入独立规则引擎或规则管理平台。配置调整通过 Git 和应用正常发布生效，不承诺运行时热更新。

### 6.2 职责与模块

| 组件 | 职责 | 所属位置 |
| --- | --- | --- |
| 校验配置与规则描述 | 接口范围、规则 ID、类型、版本、参数及适用条件 | 数据源资源配置；公共合同在 `tensor-plugin-api` |
| 通用规则实现与注册 | 必填、唯一性、枚举、范围、字段关系及跨表匹配 | `tensor-core` |
| 数据源专属规则与预期集合提供器 | 日历、停牌、财报版本等语义和依赖声明 | `tensor-plugin-tushare` 等插件 |
| 校验服务与执行器 | 创建任务、固定配置、安排依赖、执行预算和结果聚合 | `tensor-core`；装配在 `tensor-app` |
| 数据访问与证据读取 | 固定范围、只读扫描、批次/快照引用及持久化 | 现有 repository 层 |
| 页面与 API | 提交检查、显示各维度结论和可定位明细 | `tensor-app` web 层、`control-plane` |

Controller 只处理请求、调用服务与响应映射；业务判断放在规则或服务中，SQL 与扫描放在数据访问层。复用现有 `IntegrityRule`、依赖声明、受控读取、任务调度和报告持久化，不另建一套并行执行系统。

新增规则注册通过现有数据源插件能力完成，注册键为规则类型和实现版本。配置中的规则 ID 标识一次检查实例；类型选择算法；实现版本选择具体算法版本。未知类型或缺失版本在执行前报配置错误，不静默忽略。

通用规则可以通过配置生成 `IntegrityRule` 实例，专属复杂规则直接实现该接口。新增预期集合提供器作为覆盖规则的依赖，输出既有预期键合同。

### 6.3 检查范围

新增配置范围 `SYMBOL_DATE`、`EXCHANGE_DATE`、`SNAPSHOT`、`GLOBAL`，分别表示证券日期、交易所日期、指定主体的快照及全局数据集。SNAPSHOT 必须同时固定主体清单和快照时点，GLOBAL 仍需保存实际过滤条件。

这些是设计值，不能直接传给旧版本的范围枚举。实施时需同时扩展公共合同、计划器、读取层、执行器和前端；旧 `STOCK_DATE`、`STOCK_SNAPSHOT`、`NON_STOCK` 报告保留原始口径。交易所和全局接口必须得到独立执行单元，不能继续因不含单只股票而跳过。

## 7. 配置格式及逐项解释

以下是拟议配置，现有加载器尚不支持。实现时存放在独立资源目录，例如 `tensor-plugin-tushare/src/main/resources/integrity/tushare_pro/daily.yaml`，与现有数据集 YAML 通过数据集标识关联。

```yaml
dataset: tushare_pro.daily
profileVersion: 1
scope: SYMBOL_DATE
dateField: trade_date

rules:
  - id: daily.price-order
    type: OHLC_ORDER
    version: 1
    severity: ERROR
    parameters:
      open: open
      high: high
      low: low
      close: close

  - id: daily.volume
    type: NUMERIC_RANGE
    version: 1
    severity: ERROR
    parameters:
      field: vol
      minimum: 0

  - id: daily.coverage
    type: EXPECTED_KEYS
    version: 1
    parameters:
      provider: tushare.daily-trading
      insufficientEvidence: UNKNOWN
```

| 字段 | 含义 |
| --- | --- |
| `dataset` | 选择插件与接口；这里是 Tushare 日线 |
| `profileVersion` | 整份规则组合及参数的版本；改变配置时递增，并计算内容哈希 |
| `scope` | 检查按什么范围拆分执行 |
| `dateField` | 本次筛选使用的业务日期字段 |
| `rules` | 此接口附加的检查项目；已有核心身份、键和合同检查继续由框架统一加入 |
| `id` | 规则实例唯一编号，报告据此定位 |
| `type` | 已注册的规则算法类型，不是任意 Java 类名或 SQL |
| `version` | 规则实现版本，与整份配置版本分开保存 |
| `severity` | 规则确认被违反时的严重程度；`ERROR` 对应 `FAIL`，`WARNING` 对应 `WARN` |
| `parameters` | 算法参数，例如字段映射和数值上下限 |
| `provider` | 已注册的预期集合提供器 |
| `insufficientEvidence` | 依据不足时的结论；完整性规则必须保持 `UNKNOWN` |

三条规则分别表示：

1. `OHLC_ORDER`：在输入有效时检查 `low <= high`，以及开盘价、收盘价都落在 `[low, high]` 内。`open: open` 左侧为算法参数，右侧为实际字段；其他接口可映射到 `open_price`。
2. `NUMERIC_RANGE`：检查 `vol >= 0`，零值允许。上下限按包含边界处理；需要排除边界的规则必须显式配置，不猜默认含义。
3. `EXPECTED_KEYS`：使用 `tushare.daily-trading` 生成预期业务键，与实际键比较。确认缺失为 `FAIL`，候选缺口为 `WARN`，证据不足的覆盖结论为 `UNKNOWN`。

完整性规则未声明 severity 时，由注册类型规定上述结果映射；severity 只作用于有证据的违规，不改变未知、不适用或执行错误的含义。可选 `enabled` 默认 true；显式停用必须保留停用项及原因，不计为通过。

空值不能简单跳过后算 PASS：基础合同负责必填检查；业务规则声明条件必填、允许空值和适用条件。字段必填却缺失时报告 `FAIL`；来源合同允许为空且规则不适用时报告 `NOT_APPLICABLE`；缺少计算依据时报告 `UNKNOWN`。OHLC 规则需先校验行情适用条件和所需字段，不能因全部价格为空而通过。

规则类型为额外参数定义明确的加载合同，包括必填参数、允许值、字段类型、适用条件、依赖及空值处理。比较公式的精度容差必须写入参数和报告，不能依赖浮点数恰好相等。

## 8. 扩展、加载与版本管理

| 需求 | 扩展操作 |
| --- | --- |
| 改阈值或启停规则 | 修改 YAML 参数或 enabled，更新配置版本并发布 |
| 为接口增加已有检查 | 增加规则实例，配置字段映射和条件 |
| 增加复杂业务算法 | 实现并注册一个独立 Java 规则类型和版本，再从配置引用 |
| 增加接口 | 增加数据集元数据与校验配置，选择合适的已有规则或专属提供器 |
| 增加数据源 | 新插件声明自己的字段语义、适用范围、规则和依据 |

启动时校验：接口存在；规则 ID 无重复；类型和版本存在；参数符合合同；字段存在且类型兼容；依赖可解析且无环；范围与日期轴兼容。启用接口必须有明确校验配置或显式记录尚未支持的能力。将“恰好 40 项”改成当前启用接口与配置的对应关系检查。

任务受理时固定接口定义、配置版本及内容哈希、规则版本、范围和证据选择。规则配置改变不应静默改变已受理任务的口径；若固定实现不再可用，明确中断并记录原因。

报告保留原规则配置和证据引用。读取历史报告不重新套用最新规则；需要比较新旧规则时创建新的检查任务。保留版本信息能解释历史结论；只有相应数据与参考快照仍可读取时才能承诺重跑复现。

## 9. 结果、聚合及问题明细

| 结果 | 判断条件 |
| --- | --- |
| `PASS` | 规则适用、已完整执行且所需证据充分，检查满足要求 |
| `FAIL` | 有明确证据证明违反规则 |
| `WARN` | 疑似缺口、统计异常或待核实差异 |
| `UNKNOWN` | 缺少参考资料、未完整执行或无法判断 |
| `NOT_APPLICABLE` | 规则确实不适用于当前接口、主体或范围，并说明原因 |

任务和单元的排队、运行、完成、失败、中断属于执行状态，独立保留。规则异常记录执行错误及 `UNKNOWN` 数据结论，不能当作零记录或数据 FAIL；其他已确认的问题仍保留。

页面优先分别显示记录质量、采集覆盖、业务完整性及来源对账细项。现有 `KEY / FIELD` 可归入记录质量，现有 `COVERAGE` 对应业务完整性；采集覆盖是新增维度，需版本化合同，不覆盖旧字段含义。

如保留单一总览，沿用 `FAIL > UNKNOWN > WARN > PASS` 的显式聚合规则，N/A 不参与；全部 N/A 显示 N/A。总览不得替代三类结论及各状态数量。停用或未执行规则不伪装成 N/A 或 PASS；无异常但证据不足仍可显示“记录质量通过，完整性无法判定”。

问题明细至少包含检查及规则 ID、接口、股票或交易所、范围、业务键、字段、实际值、预期值或约束、结果、`reasonCode`、中文解释、规则与配置版本、证据引用和建议处理方式。没有可确定实际值或预期值时保留空值并说明原因，不编造。

计数需说明是记录数、唯一业务键数还是问题数。一行可有多个问题，不能直接把问题数当作坏记录数。明细被截断、扫描预算耗尽或查询失败时，保存已发现的问题、未完成标记和原因，不给出完整通过结论。

## 10. 执行与性能约束

- 先固定计划和所需依赖，再执行检查；依赖不满足只影响相关规则，独立的记录质量规则仍可运行。
- 保留现有同一读取快照和预算机制。任务不声称所有单元共享同一数据库全局快照；报告记录各单元读取时点。
- 目标扫描与键比较按适当分区执行，支持批量读取及有界索引。现有评估器会累积目标批次，扩大到全市场前需处理内存上限，不能把“分页取数”视为已实现有界内存。
- 复用同一快照中合法的参考读取，避免每条规则重复扫描。时间、扫描行数、问题明细和并发都受预算限制。
- 增量检查先覆盖本次新增或更新的范围；涉及前后关系、周月聚合或财报版本时扩展必要依赖窗口。历史回扫单独执行。
- 校验只生成结论及补采建议；自动修改或删除源数据、自动补数和定时巡检不属于本次方案归档交付。

## 11. 分阶段实施与验收

### 阶段一：真实问题定位和可解释结果

取得真实 FAIL 报告并复现；区分数据问题、元数据错误、规则错误与执行异常；补齐实际值、预期值和依据的展示。保持 UNKNOWN 的真实含义，设计非股票范围的任务与读取合同。

### 阶段二：完成基础闭环

优先 `trade_cal`、`stock_basic`、`daily`、`daily_basic`，实现配置加载、规则注册、基础规则、预期集合策略和三维报告。依赖暂不足时明确显示待补依据，不能为了让页面变绿降低判定标准。

### 阶段三：覆盖全部接口

按策略矩阵补齐各接口配置和专属判断，加入财报版本、事件类采集证据与来源对账，支持增量检查及历史回扫。实际支持列表由配置与接口注册共同决定。

### 必须通过的验收场景

| 场景 | 预期结果 |
| --- | --- |
| 正常且依据充分的日线数据 | 适用规则通过，可确定的完整性通过 |
| 已证明为全天停牌且按来源口径不应有日线 | 不报确认缺失 |
| 停牌依据或交易日历缺失 | 对应覆盖 UNKNOWN，独立质量规则继续 |
| 亏损公司的 PE 为空 | 按合法空值处理，不报必填错误 |
| 无事件，本地为空，但缺少来源全集证据 | 不确认缺失，也不宣称完整；业务完整性 UNKNOWN |
| 可靠预期为空且本地为空 | 已验证为空，覆盖率不伪造 100% |
| 同报告期存在合法报表类型或修订版本 | 不按简单季度键误报重复 |
| 删除一条已确认应存在的行情 | FAIL，定位股票、日期和确认依据 |
| 制造完整业务键重复或来源标识错误 | FAIL，定位具体记录与规则 |
| 最高价低于最低价、成交量为负 | 对应规则 FAIL，显示实际值与约束 |
| 到达来源返回上限，无法证明分页或拆分完整 | 采集覆盖或对应完整性 UNKNOWN，不能认作正常空数据 |
| 扫描超时、规则异常或明细超过上限 | 执行或明细标为未完成，保留问题，不汇总为完整 PASS |
| 非股票级接口 | 按交易所或全局范围执行，不直接跳过 |
| 修改阈值或新增已注册规则配置 | 不改执行器业务代码即可生效，历史报告口径保持原样 |
| 新增一种复杂规则实现 | 注册并配置后可执行，不向 Controller 堆叠业务逻辑 |
| 新增接口 | 不再因硬编码“40 项”失败，缺配置时给出明确原因 |

验收同时包含人工构造的正常/异常边界样本和真实来源样本。接口模板只是样本，不能作为完整数据全集。单元及集成测试验证业务结论，页面测试验证状态解释和问题定位。文档提交本身不表示这些运行时验收已经完成。
