# Tensor 模块化实施路线图设计

| 文档信息 | 内容 |
|---|---|
| 日期 | 2026-08-25 |
| 状态 | 待用户复核 |
| 估算口径 | 单个 AI 编码代理的有效执行工时 |
| 实施策略 | 契约优先、语言隔离、模块完成后集成 |

## 1. 目标

基于以下需求和技术基线，形成一份可以由 AI 编码代理逐任务执行的推进路线图：

- `docs/design/Tensor_多源证券数据平台_BRD_v1.0.md`，正文版本 v1.5；
- `docs/design/Tensor_多源证券数据平台_PRD_v1.0.md`，版本 v1.0；
- `docs/design/Tensor_多源证券数据平台_TRD_v1.0.md`，版本 v1.0；
- `docs/data-template/manifest.json` 和 49 份数据模板。

路线图必须满足：

1. 工作按模块组织，各模块先独立实现并通过自身验收，再进入集成阶段；
2. 单个任务只处理一种主要语言，减少 Java、SQL、YAML、Vue 在同一上下文中相互挤占；
3. 每个任务实施前具有完整、唯一、可验证的任务设计，能够在一次聚焦工作中完成实现、测试和复核；
4. 设计没有明确做什么、怎么做、如何测试、如何验证或依赖什么信息时，先修订对应任务设计，不在实现过程中猜测；
5. 实现过程中不临时拆分任务，也不通过修改路线图改变既定目标、交付物或验收条件；
6. 每项 BRD、PRD 和 TRD 要求都能追踪到实施任务和验收证据；
7. 工时使用 AI 有效执行工时，不使用人类研发工日作为主估算单位。

## 2. 当前基线

当前仓库仍接近脚手架状态：

- `control-plane` 只有 Vue/Vite 示例结构，尚未引入路由、Element Plus、Axios 和测试体系；
- `data-plane` 只有单模块 Maven POM 和示例 Java 入口，尚未形成 TRD 定义的五个 Maven 模块；
- 49 份 JSON 模板已经存在，可作为元数据和表字段基线；
- 当前工作目录不包含 Git 元数据，无法读取近期提交历史或在此目录提交路线图文档。

因此路线图从工程基线、契约和模块骨架开始，不假设已有业务实现可复用。

## 3. 采用的拆分策略

采用“契约优先、语言隔离、模块验收后集成”。

### 3.1 契约优先

先冻结跨模块共享但不包含实现的契约：

- Java SPI 和领域对象的公共语义；
- 49 个数据集 YAML 的 schema、字段、业务键和筛选定义；
- REST 请求、响应和错误包络；
- Flyway 表结构与数据集定义的一致性规则；
- 前端只依赖的 API DTO 和页面状态约定。

后续模块只读取本模块契约，不通过阅读其他语言的实现来推断行为。

### 3.2 语言隔离

| 任务类型 | 允许的主要输入 | 禁止作为常规输入 |
|---|---|---|
| Java | Java 接口、Java 实现、相关契约摘要 | Vue 组件源码、完整 SQL 迁移正文 |
| SQL | 数据集定义、字段基线、业务键清单 | Java 服务实现、Vue 组件源码 |
| YAML | JSON 模板、元数据 schema、PRD 参数表 | Java 和 Vue 实现 |
| Vue/JavaScript | REST/DTO 契约、交互需求、前端模块源码 | Java 服务内部实现、Flyway 迁移正文 |
| 集成测试 | 稳定接口、构建命令、测试报告 | 全量读取所有模块实现 |

确实需要跨语言验证时，由集成任务执行黑盒测试。缺陷修复回到对应语言模块的新任务中完成。

### 3.3 模块完成后集成

模块达到以下条件才可声明完成：

1. 模块公开接口或产物已固定；
2. 模块内自动化测试通过；
3. 模块不依赖尚未声明的其他模块实现细节；
4. 需求追踪项具有可引用的测试或检查证据；
5. 上下游只需读取契约即可使用该模块。

集成阶段不承担大规模功能实现，只负责装配、黑盒验证、缺陷定位和发布门禁。

## 4. 任务设计完整性

每个预定义任务在实施前必须拥有 `docs/task-designs/<任务编号>-designs.md`。设计只包含 `做什么`、`怎么做`、`如何测试`、`如何验证`、`依赖什么信息` 五个固定部分，并与对应任务卡双向链接。

模块计划列出的文件、章节和接口是任务设计的候选输入，不是当前状态或运行时授权。设计无法唯一说明实现方式、测试方法、验证标准或必要依赖时，先修订任务设计，再开始实现。

单个任务保持 0.5～4 AI 小时，并在设计中列出完成实现与验证所需的最小输入。任务目标、交付物或验收发生实质变化时修改任务设计和路线图，不通过编辑路线图记录运行时状态。

## 5. AI 工时口径

一个 AI 小时指代理实际用于以下活动的累计时间：

- 阅读任务限定上下文；
- 编写失败测试；
- 实现与修改；
- 执行测试、分析失败和修复；
- 自检需求覆盖、差异和文档。

不计入：等待用户回复、等待权限批准、真实 Tushare 服务不可用造成的外部等待，以及 CI 排队等待。外部等待单独作为进度风险记录。

单任务工时分级：

| 级别 | AI 工时 | 适用范围 |
|---|---:|---|
| XS | 0.5～1 小时 | 单一配置、契约检查或小型测试闭环 |
| S | 1～2 小时 | 单个明确接口或单一组件闭环 |
| M | 2～3 小时 | 一个聚焦领域能力及其完整测试 |
| L | 3～4 小时 | 有集成测试但仍局限于单模块、单语言的能力 |

不允许创建超过 4 AI 小时的执行任务。

## 6. 模块结构与推进顺序

| 编号 | 模块 | 主要语言 | 独立交付物 | 前置模块 | 初步 AI 工时 |
|---|---|---|---|---|---:|
| M00 | 需求追踪与共享契约 | Markdown/JSON Schema | 追踪索引、元数据 schema、REST 契约 | 无 | 3～5 |
| M01 | 后端工程基线 | XML/Java | Maven 聚合、五模块骨架、测试和依赖门禁 | M00 | 4～6 |
| M02 | `tensor-plugin-api` | Java | SPI、值对象、描述符、包络、适配批次 | M01 | 8～12 |
| M03 | Tushare 数据集元数据 | YAML | 49 个数据集定义及模板契约测试 | M00、M02 契约 | 16～24 |
| M04 | MySQL/Flyway | SQL | 49 张表、唯一键、索引和结构验证 | M03 | 18～28 |
| M05 | `tensor-core` 注册与适配 | Java | 注册表、目录、参数校验、通用适配器 | M02、M03 | 14～20 |
| M06 | `tensor-core` 持久化与查询 | Java | 事务 Upsert、计数、数据集锁、分页查询 | M02、M03、M04 | 18～26 |
| M07 | `tensor-plugin-tushare` | Java | HTTP 客户端、49 接口调用、错误分类 | M02、M03 | 10～14 |
| M08 | `tensor-plugin-fixture` | Java | 成功、空、上游失败、适配失败和回滚场景 | M02、M03、M04 | 7～10 |
| M09 | `tensor-app` | Java | REST、配置、异常、请求标识、指标、健康检查 | M05～M08 | 12～18 |
| M10 | 前端工程基线 | JavaScript/Vue | 路由、Element Plus、Axios、测试体系、布局 | M00 REST 契约 | 7～10 |
| M11 | 数据下载页面 | Vue | 元数据驱动表单、提交状态和结果反馈 | M10、M00 REST 契约 | 10～14 |
| M12 | 数据查看页面 | Vue | 动态筛选、宽表、分页、查询状态 | M10、M00 REST 契约 | 12～18 |
| M13 | 构建、打包与运行 | Maven/配置 | 前端静态资源进入单 JAR、启动和配置说明 | M01、M09～M12 | 7～10 |
| M14 | 系统集成与发布验证 | 测试编排 | E2E、49 接口回归、性能、安全和发布报告 | M03～M13 | 24～38 |

初步总量为 **170～253 AI 小时**。正式路线图将把每个模块预先拆成不超过 4 小时的任务，再按依赖关系计算关键路径；该区间不等同于自然日工期。

## 7. 预先规划的模块内边界

模块可以包含多个任务，但所有任务必须在模块实施开始前完成切分和任务设计。

- M03 按 BRD/PRD 的八个业务分类预先形成 YAML 任务；财务宽表根据候选输入规模在开始前进一步按接口组形成任务。
- M04 按 TRD 9.6 的 Flyway 迁移组形成 SQL 任务，不在写迁移过程中临时拆表。
- M05 按注册表、参数校验、元数据目录、类型转换和适配批次形成 Java 任务。
- M06 按 SQL 模板、事务 Upsert、计数与锁、查询校验、分页读取形成 Java 任务。
- M07 按客户端协议、返回校验、错误分类和插件装配形成 Java 任务。
- M09 按元数据 API、下载 API、查询 API、异常与安全、可观测性形成 Java 任务。
- M11 和 M12 按页面状态与组件职责形成 Vue 任务，但单个任务不得同时修改后端 Java。
- M14 的缺陷只负责定位和登记；修复以对应模块、对应语言的独立任务执行。

每个模块任务实施前都必须具有完整、唯一、可验证的任务设计。任务卡信息不足时先修订对应设计，再开始实现。

## 8. 集成门禁

### 8.1 模块门禁

进入 M14 前必须满足：

- M02 的 SPI 和领域契约测试通过；
- M03 的 49/49 元数据与 JSON 模板字段、顺序、参数和业务键契约通过；
- M04 的 MySQL 8.4 Flyway 迁移和实际 schema 校验通过；
- M05～M09 的后端单元、架构、WireMock、Testcontainers 和 API 测试通过；
- M10～M12 的前端组件测试通过；
- M13 能产生包含 Vue 静态资源、49 个 YAML 和 Flyway SQL 的单个 JAR。

### 8.2 集成顺序

1. fixture 插件端到端闭环；
2. 数据下载页面与后端下载 API；
3. 数据查看页面与后端查询 API；
4. 成功、空数据、鉴权、适配失败、数据库回滚和重复下载场景；
5. 49 接口自动契约和页面回归；
6. `daily` 性能场景和 `balancesheet` 152 列宽表场景；
7. 全新环境启动、Token 脱敏、安全与发布准入。

## 9. 路线图任务卡格式

正式路线图中的每个任务必须包含：

- 唯一任务编号和所属模块；
- AI 工时等级与估算范围；
- 对应 BRD、PRD、TRD 条目；
- 前置任务及其稳定接口；
- 独立任务设计文档 `docs/task-designs/<任务编号>-designs.md` 的路径和双向链接；
- 候选输入文件、章节或接口及其用途；
- 创建、修改和测试文件清单；
- 明确的输入、输出和类型签名；
- 失败测试、实现、验证和差异检查步骤；
- 精确测试命令与预期结果；
- 独立验收条件；
- 对未决设计、项目范围和禁止混入事项的明确说明。

路线图任务卡只描述项目计划，不记录当前执行状态、授权、事件、归档或恢复信息。

## 10. 追踪与完成标准

正式路线图建立以下双向追踪：

```text
BRD FR-01～FR-09
  -> PRD-F-001～PRD-F-031 / AC-001～AC-018 / 非功能要求
  -> TRD 章节、类、接口、表、测试门槛
  -> 模块编号
  -> 执行任务编号
  -> 自动化测试或手工验收证据
```

路线图完成必须满足：

1. BRD FR-01～FR-09 无遗漏；
2. PRD-F-001～031 和 AC-001～018 均有任务承接；
3. TRD 的架构、49 数据集、事务、查询、REST、前端、安全、可观测性、性能、构建和测试要求均有任务承接；
4. 所有执行任务在开始前已经拆到 0.5～4 AI 小时；
5. 所有任务都有独立五段式设计文档，且任务卡与设计文档双向链接；
6. 项目任务索引、任务设计和模块计划职责清晰且链接有效；
7. 所有模块先通过独立门禁，再进入系统集成；
8. 不把范围外能力加入首期路线图。

## 11. 明确不采用的方式

- 不按“后端全部实现”形成一个大任务；
- 不按端到端页面功能把 Java、SQL 和 Vue 混入同一执行任务；
- 不把 BRD、PRD、TRD、49 模板和全仓源码同时列为单个任务的常规输入；
- 不把完整总路线图、全部模块计划、全部任务设计和完整任务索引列为单个任务的常规候选输入；
- 不在设计结论不唯一时修改生产实现；
- 不把补充设计和生产实现混在同一任务中；
- 不在任务执行过程中临时拆分剩余工作；
- 不在集成任务中顺手修改多个语言模块；
- 不将定时任务、任务队列、登录权限、导出、插件市场等首期范围外能力提前实现。
