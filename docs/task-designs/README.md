# 任务设计文档目录

每个预定义实施任务使用一份独立的项目设计文档：

```text
docs/task-designs/<任务编号>-designs.md
```

例如：

```text
docs/task-designs/M00-T01-designs.md
docs/task-designs/M06-T04-designs.md
docs/task-designs/M14-T08-designs.md
```

## 最低内容要求

每份设计文档只包含以下五个稳定标题：

1. `做什么`
2. `怎么做`
3. `如何测试`
4. `如何验证`
5. `依赖什么信息`

每个部分至少回答以下问题：

| 部分 | 最低要求 |
|---|---|
| 做什么 | 产物是什么、范围是什么、不做什么、完成后能观察到什么 |
| 怎么做 | 修改哪些文件或接口、核心流程是什么、边界和失败规则是什么 |
| 如何测试 | 测试哪些正常、异常、边界和回归场景，各自预期什么结果 |
| 如何验证 | 用什么验收标准和质量门禁确认任务完成、范围未越界、证据可追踪 |
| 依赖什么信息 | 依赖项是什么、用于解决什么问题、稳定接口或版本是什么、前置条件是什么 |

## 复杂度伸缩

- 文档或配置类简单任务可以只写简短段落和列表。
- 代码类任务可在五个固定标题下增加三级标题、表格、接口签名或流程图，但不得增加新的二级标题。
- 一个任务无法在五个部分内形成唯一且可执行的结论时，应继续拆分任务，而不是无限扩充设计文档。

## 设计就绪门禁

只有以下问题都能明确回答，任务才可以进入实施：

1. 开发者是否知道最终产物和范围？
2. 开发者是否知道修改位置、接口、核心流程和失败行为？
3. 开发者是否知道需要覆盖的测试场景及预期结果？
4. 开发者是否知道如何判定任务完成并提供证据？
5. 开发者是否能定位全部必要依赖及其用途？

任何一项需要实施者自行猜测，都应先修订设计。

## 自动检查

- 文件名必须符合 `docs/task-designs/<任务编号>-designs.md`。
- 设计文档必须且只能包含五个固定二级标题。
- 任务卡必须通过 `Design` 字段链接设计文档，设计文档顶部必须链接回任务卡。
- 同一任务只能对应一份设计文档。
- 设计文档不得包含未决占位内容、执行状态或实际测试结果。

## 使用说明

- “如何测试”证明实现行为正确；“如何验证”证明任务目标完成、范围未越界且证据可追踪。
- 依赖项必须说明用途，不能只列文件名或任务编号。
- 设计文档不记录执行状态、权限、事件、归档、恢复、实际测试结果或验收记录。
