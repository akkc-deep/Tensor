# M14-T08 AC 映射与发布证据收尾——任务设计

任务编号：`M14-T08`。权威来源：[任务看板 M14-T08](../task-handoffs/tensor-v1/tensor-v1-task-board.md#m14-t08)，Order 79；[任务卡](../superpowers/plans/tensor-modules/M14-integration-release.md#task-m14-t08-ac-映射与发布证据收尾)。本设计按用户明确要求收窄为现有证据的文档交付，任务状态与实际结果由看板和验收文件记录。

## 做什么

整理已有验收记录，为 AC-001～018 建立可追踪映射，交付三份相互链接的文档。每条结论注明证据日期、源码/产物版本及覆盖局限；允许如实记录部分覆盖、失败和未验证项，文档完成以记录准确、完整为标准。

| 产物 | 固定内容 |
|---|---|
| `docs/verification/release-checklist.md` | 范围与结论、证据索引、门禁汇总、延期与风险、文档核对。证据索引记录来源路径、原任务/issue、原验证时间、命令与退出码、测试计数、原提交/JAR 散列及局限；未记载字段填写“原记录未提供”。 |
| `docs/verification/ac-001-018.md` | 映射口径、18 项 AC 表、PRD-F-001～031 表、PRD 10.1～10.6 表。每行保留原要求/优先级，写明来源、可支持的结论、覆盖程度和当前版本未复验事实。 |
| `docs/verification/release-summary.md` | 文档交付结论、已有证据摘要、未验证项与风险、运行说明及前两份文档链接。固定说明“已有证据完成归档，当前候选版本尚未完成本轮整体验收”；不据此指定一个已验证的发布候选包。 |

本任务不执行候选源码冻结、重建/打包、验收脚本接入、Maven/npm/Playwright 回归、全新环境首跑、安全复扫或真实接口复验；不启动 JVM/数据库/浏览器，不读取 Token 或新增真实请求，不修改生产代码、测试工具和历史验收结果。原第 1～5 项不再是本任务的执行范围或完成前提，也不因本次收窄新增这些子任务。

保留 49 项自动契约和 M14-T09 固定 40 接口的已有证据。ISSUE-008 九项真实接口及 ISSUE-009 性能验证仍为“不依赖，用户后续单独处理”；ISSUE-015 已接受风险仅按原记录归档，不改写为漏洞修复、扫描通过或对新产物的风险接受。

## 怎么做

1. 完整读取“依赖什么信息”列出的权威定义及已有验收文档，按原验证轮次建立证据索引。复制原记录中的安全摘要和已有命令/计数，不执行这些命令，也不读取原始业务数据或凭证。记录引用文档的当前 SHA-256，并与文档中所述源码/JAR/原始报告散列分栏，不能混用。
2. 每份证据独立保留原提交、JAR 类型/散列、时间和运行结果。不同版本的 49 契约、40 接口、UI 和安全专项结果分别列示；不合并成“同一候选包全部通过”。没有版本字段或私有临时报告已不可定位时，明确记录此局限；不重建产物、不要求恢复临时环境。
3. `release-checklist.md` 将“原执行结果”和“当前处置/适用性”分开。原结果沿用来源中的通过、失败、未运行及原始退出码；处置注明历史证据、本次未复验、原记录未提供、用户延期或用户接受风险。缺少当前版本验证是需披露的事实，不阻止本任务文档交付。
4. `ac-001-018.md` 按 PRD 原编号和标题逐项映射，覆盖程度仅取“已有证据支持”“部分支持”“无可用证据”；均另列“本次未复验”。“已有证据支持”只对所列原版本/场景有效，不等于当前版本验收通过。AC-018 只能说明已有首跑与各页面记录的组合范围，缺少同一候选版本全新环境完整验收时记录为部分支持，不补造整体验收。
5. 基于既有需求追踪索引，保留全部 PRD-F-001～031 的 P0/P1 和直接/部分/内联映射语义，以及 PRD 10.1～10.6。不能用“对应 AC 有证据”推断其内联要求全部满足；来源不足的条目如实标记。原 49 真实验收与性能目标不算通过，性能数值只在原证据确有测量时引用。
6. 单列 ISSUE-008 的九接口：`top_inst`、`broker_recommend`、`share_float`、`hs_const`、`moneyflow_hsgt`、`hk_hold`、`index_member`、`hsgt_top10`、`namechange`。M14-T09 原同轮 40 通过/0 失败/0 未运行、48 次下载/80 次查询及 fixture 2/3 只作为已归档历史结果；不与其他轮拼接，不调用接口验证权限或数据变化。
7. 安全部分同时引用 M14-T07 原失败报告、ISSUE-010～014 各专项修复验证和 ISSUE-015 原风险接受决定。保留安全脚本原退出码、专项范围、35 条高阈值发现/27 个不同 CVE 和四类分析缺口；“issue 已完成”与“整体验收通过”分开，不将不同包的专项结果拼成一次新的整体安全通过。
8. `release-summary.md` 汇总上述证据与局限，不宣称发布就绪。ISSUE-001～003、ISSUE-016 等其他问题沿用问题索引当前状态，按已有影响描述记录；不关闭 issue、不新增风险豁免，也不要求在本任务解决全部问题。
9. 三份文档只写已有脱敏摘要、证据引用和结果，不复制真实行、完整响应、私有配置或原始日志。读不到来源时记录“不可定位”并明确不可支持的结论；已知来源之间有版本差异时分列，有无法解释的事实矛盾时保留两方引用并标注，不能任选一方写成通过。

## 如何测试

本任务只做文档核对，不创建产品测试或运行原发布门禁。使用临时只读检查或人工逐项核对：

- 从 PRD 读取 AC-001～018 与 PRD-F-001～031，检查交付表的编号集合恰好一致、无重复/遗漏、标题和 P0/P1 与原定义相同；非功能映射覆盖 10.1～10.6。
- 检查三个交付文件存在且相互链接，全部仓库内来源路径可访问。逐项对照引用原文中的命令、日期、退出码、测试数和 JAR/提交散列；缺失字段或不可定位的私有产物必须明确披露，不算新验证失败或新通过。
- 核对 49 自动契约与 40 真实接口分列，九项排除与 ISSUE-008 精确一致，ISSUE-009 未实测事实保留，ISSUE-015 的原失败与接受范围均可定位。
- 检查所有 AC 行均标明本次未复验；AC-018 和发布摘要没有将不同版本/专项结果称作同一候选整体验收通过。检查三份文档只含脱敏摘要，没有新增真实行、凭证、完整响应或日志。
- 运行 `git diff --check`，检查差异限于三份交付文档及本任务必要的看板收尾记录，新增交付文件加入 Git。文档检查的实际命令和结果记录在 `release-checklist.md`，不冒充 Maven/浏览器/真实接口的新执行结果。

## 如何验证

三份交付文档形成完整、准确、可追踪的现有证据索引；18 项 AC、31 项功能需求和六类非功能要求均有明确的证据覆盖判断与局限；版本差异、缺失证据、历史失败、用户延期和风险接受被如实披露，即满足本任务验收。

本任务可在存在产品验证缺口时完成，完成仅表示 AC 映射与发布证据收尾。最终固定区分两个结论：“文档交付完成”与“当前候选版本尚未完成本轮整体验收”。不要求先解决 ISSUE-008/009、不要求复跑其他门禁，也不据此声明原 49 接口真实目标、性能目标、安全整体验收或发布准入通过。

实施时按权威看板允许的状态转换记录启动和完成；范围修订本身不代表开始或完成文档交付。达到上述验收后才记录 `IN_PROGRESS -> COMPLETED`；M14-T05 的历史 BLOCKED 和其他任务状态不因本任务收尾而改变。不为已讨论但未登记的第 1～5 项创建后继任务或交接。
