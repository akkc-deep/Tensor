## 方案A：保留默认返回，100仅作工程拆分阈值（推荐）

1. 默认分类定义为**一次普通请求中上游实际返回的分类**；当前两股票SINGLE/RANGE均观察到P/D/I，不宣称默认P或上游保证所有历史分类齐全。不传type，不分别请求P/D/I后合并。继续保留bz_code和原业务键，不做键迁移。
2. SINGLE继续为单次快照：接收来源本次返回的150行，不承诺全历史提取，也不限制或补齐为100/150行。
3. RANGE采用100作为保守的**工程拆分阈值**：每片原始行数<100按此明确接受的口径视为完整；达到或超过100先按日期拆分，单日仍满额则完整性未确认失败。150不成为新阈值。该采用口径不是Tushare已经确认的新合同，不能消除文档与实测差异。
4. 本决定仅限fina_mainbz；限定修订T13/T14的默认分类及完整性采用条款。保留原16case，4个满额观察不升级PASS。按已观察的20250630另登记两股票20250629～20250701整段SOURCE（来源补证独立于本决定执行），与既有单日及上下边界组成可执行任务样本；2025全年和六年宽窗口仍保留待任务拆分验证。
5. 规则、来源及任务输入交给ISSUE-026；生产仍NEEDS_VERIFICATION/v1，只有匹配候选包的真实TASK/SQL通过后开放。本决定不关闭母issue。

**与原严格验收的差异：** 原要求可核验的默认集合及实际截断合同；本方案接受上游原样默认返回和保守工程阈值，不再等待上游补充默认集合/硬上限保证。范围内样本有效性、业务键计数、实际任务/SQL要求全部保留。

## 方案B：保持严格合同，等待上游补证

保留既有参数与未验证状态，要求上游明确省略type的集合，以及普通单股票SINGLE/RANGE为何返回110/150、实际截断信号和适用范围。现有证据全部保留，ISSUE-020暂不能关闭。未授权联系第三方，本轮不发送消息。

如果产品实际只需要P、D或I中的一种，则须另作明确参数/数据范围决定并修订设计；这不包含在方案A/B中，不能由实现自行选择P。
